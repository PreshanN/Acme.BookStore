# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An ABP Framework 10.6.1 layered (DDD) solution on .NET 10, MVC/Razor Pages UI (LeptonX Lite theme), PostgreSQL via EF Core, multi-tenancy enabled. It was generated by ABP Studio (`abp new ... -t app --ui-framework mvc --database-provider ef --database-management-system postgresql`) and then extended with an **Employee Management** domain (Employees, Departments) that is the real custom code here. The Books/Authors CRUD sample from the template is only partially present (see "Current state").

`.cursor/rules/` holds ABP's own generated guidance (DDD patterns, layer rules, EF Core, MVC, testing, CLI). It is accurate for this solution; consult it for ABP idioms rather than re-deriving them. `.vscode/mcp.json` wires the `abp mcp-studio` MCP server (ABP Studio must be running).

## Commands

Solution file is `Acme.BookStore.slnx` (XML solution format; `dotnet build` with no args works from the root).

```bash
dotnet build                                   # whole solution
dotnet run --project src/Acme.BookStore.Web    # https://localhost:44340 (Swagger at /swagger)
dotnet run --project src/Acme.BookStore.DbMigrator   # apply migrations + seed (admin / 1q2w3E*)
abp install-libs                               # client-side libs into Web/wwwroot/libs; needed after clone
```

Tests (xUnit + Shouldly + NSubstitute):

```bash
dotnet test                                                        # all test projects
dotnet test test/Acme.BookStore.EntityFrameworkCore.Tests          # the project that actually runs app-service tests
dotnet test --filter "FullyQualifiedName~BookAppService_Tests"     # one class
dotnet test --filter "FullyQualifiedName~Should_Create_A_Valid_Book"  # one test
```

EF Core migrations are run from the EF Core project. The design-time factory reads the connection string from `src/Acme.BookStore.DbMigrator/appsettings.json`, so that file must point at a reachable PostgreSQL:

```bash
cd src/Acme.BookStore.EntityFrameworkCore
dotnet ef migrations add <Name>
dotnet run --project ../Acme.BookStore.DbMigrator      # preferred over `dotnet ef database update` (also seeds)
```

ABP Studio run profile (`etc/abp-studio/run-profiles/Default.abprun.json`) defines two tasks backed by `etc/scripts/`: **Initialize Solution** (`initialize-solution.ps1`: build, install-libs, DbMigrator, dev cert) and **Migrate Database** (`migrate-database.ps1`). Health endpoints: `/health-status`, `/health-ui`.

Gotcha: if the Web app is running under IIS Express (Visual Studio), `dotnet build` fails with MSB3021/MSB3027 file-lock errors on the Web project. That is not a compile error; stop the debugger first.

## Architecture

### Module chain

Every project has one `*Module` class with `[DependsOn]`; the Web project is the single host and pulls everything in:

```
Domain.Shared  ->  Domain  ->  Application  ->  Web (host)
                     ^            ^               ^
Application.Contracts -----------+               |
EntityFrameworkCore (depends on Domain) ---------+
HttpApi (depends on Contracts) ------------------+
```

- **No hand-written controllers.** `BookStoreWebModule.ConfigureAutoApiControllers` turns every `IApplicationService` in the Application assembly into REST endpoints (`/api/app/<service>/...`). The HttpApi project only holds the `BookStoreController` base class and localization wiring. Razor page JS calls these via generated proxies (`acme.bookStore.books.book.getList`, etc.).
- `BookStoreDbContext` replaces the Identity and TenantManagement DbContexts (`[ReplaceDbContext]`) so those module tables live in the same database and can be joined.
- `AddDefaultRepositories(includeAllEntities: true)` means `IRepository<TEntity, Guid>` is available for every entity, not just aggregate roots.
- **The Web app migrates the database on startup** (`BookStoreWebModule.OnApplicationInitializationAsync` calls `BookStoreDbMigrationService.MigrateAsync`), in addition to DbMigrator.
- Npgsql legacy timestamp behaviour is switched on in both the EF module and the design-time factory; keep both in sync if you touch it.

### Employee Management domain (the custom code)

Follows the rich-domain-model style from `.cursor/rules/framework/common/ddd-patterns.mdc`:

- **Aggregates** `Employee` and `Department` (`FullAuditedAggregateRoot<Guid>`, `IMultiTenant`, `[Audited]`). State changes go through methods (`SetSalary`, `ChangeAddress`, `AssignToDepartment`, `AddTeam`, ...) which throw `BusinessException` with `BookStore:*` codes. Child collections (`Qualifications`, `Teams`) are private lists exposed read-only; EF maps them with `.HasField("_teams")`.
- **Value objects** in `Domain/Shared/ValueObjects/` (`Money`, `EmailAddress`, `Address`) and `ContactInfo` are mapped as EF **owned types** with explicit column names (`SalaryAmount`, `Email`, `AddressLine1`, `ContactEmail`...). Note the namespace is `Acme.BookStore.Shared.*` even though the files live in the Domain project, not Domain.Shared.
- **Domain services** `EmployeeManager` / `DepartmentManager` own cross-aggregate rules (unique employee code, unique department name, department-must-exist). App services never `new` an aggregate directly for creation; they call the manager.
- **Custom repositories** `IEmployeeRepository` / `IDepartmentRepository` (Domain) with `EfCore*Repository` implementations that use `EF.Functions.ILike` for filtering (PostgreSQL-specific; SQLite tests will not exercise that path) and `System.Linq.Dynamic.Core` for sorting.
- **Application services** inherit `BookStoreAppService` and are class-level `[Authorize(BookStorePermissions.X.Default)]` with per-method permissions. `EmployeeAppService` redacts `SalaryAmount`/`SalaryCurrency` unless the caller has `BookStore.Employees.ViewSalary`. Permissions are defined in `Application.Contracts/Permissions/`.
- **Validation**: DTOs use data annotations (enforced by ABP; `AbpValidationException`). There are also FluentValidation `*DtoValidator` classes in Application, but only the raw `FluentValidation` package is referenced, not `Volo.Abp.FluentValidation`, so ABP never runs them. Either add that module or treat the validators as dead code.
- **Mapping is Mapperly**, via `Volo.Abp.Mapperly` `MapperBase<TSource, TDest>` subclasses (`EmployeeToEmployeeDtoMapper`, `DepartmentToDepartmentDtoMapper`, `BookStoreApplicationMappers.cs`). `ObjectMapper.Map<,>()` resolves to these. The `EmployeeManagementSystemApplicationAutoMapperProfile` class and the AutoMapper package reference are vestigial: no module depends on `AbpAutoMapperModule`, so that profile is never used. Add new mappings as Mapperly mappers.
- Tables use prefix `App` (`BookStoreConsts.DbTablePrefix`) and no schema. Auditing is enabled with entity-history for `Employee` only (`BookStoreDomainModule`).
- `DepartmentDataSeedContributor` seeds a "General" department per tenant; `BookStoreDataSeederContributor` seeds the sample authors/books that tests assert on (e.g. "1984").

### Test topology

- `Acme.BookStore.Application.Tests` contains **abstract** generic test classes (`BookAppService_Tests<TStartupModule>`). They are instantiated in `Acme.BookStore.EntityFrameworkCore.Tests` (e.g. `EfCoreBookAppService_Tests`) against an in-memory **SQLite** database created from the DbContext model (not from migrations). So the EF Core test project is where application-level tests actually execute; `dotnet test` on Application.Tests alone runs little.
- `BookStoreTestBaseModule` registers `AddAlwaysAllowAuthorization()` and runs all `IDataSeedContributor`s once at startup, so seed data is present and permission attributes do not block tests.
- `Acme.BookStore.Web.Tests` spins up the real Web module with `AbpAspNetCoreTestBaseModule` and hits pages over HTTP.

## Current state (as of October 2026, uncommitted work in progress)

Things a new session should know before trusting the tree:

- `IBookAppService` / `IAuthorAppService`, their DTOs, Razor pages under `Web/Pages/Books` and `Web/Pages/Authors`, Mapperly mappers and `BookAppService_Tests` all exist, but **there is no `BookAppService` or `AuthorAppService` implementation** in `src/`. Those tests and pages will fail at DI resolution until one is added (or they are removed).
- `EntityFrameworkCore/EntityTypeConfigurations/*Configuration.cs` (untracked) duplicate the inline `builder.Entity<...>` blocks in `BookStoreDbContext.OnModelCreating` and are **not applied** (no `ApplyConfiguration` / `ApplyConfigurationsFromAssembly` call). The inline blocks are what the model and migrations currently reflect. Also note `builder.Entity<DepartmentTeamConfiguration>(...)` in the DbContext registers the configuration class itself as an entity; it should be `DepartmentTeam`.
- `BookStoreAppService` (the shared base class) currently takes `IEmployeeRepository`/`EmployeeManager` in its constructor and carries Employee-specific methods, so every app service (including `DepartmentAppService`) must pass those in. Expect this to be refactored.
- The `Department_DataAccess` migration and the `DepartmentDataSeedContributor` are untracked; run DbMigrator after pulling.
